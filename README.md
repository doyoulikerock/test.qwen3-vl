# vidsearch

Qwen3-VL(`Embedding-2B` + `Reranker-2B`)로 로컬 영상 속 장면을 자연어(한국어/영어)로 검색하고,
`4B-Instruct`로 특정 구간에 대해 자유롭게 질문하는 CLI 프로토타입.
전부 로컬 GPU에서 돌아가며, 영상 파일이 외부로 나가지 않는다.

설계 배경과 실측 검증 과정(왜 2B를 골랐는지, 리랭커가 왜 필요한지, 클립 임베딩으로 동작 질의를 어떻게 잡았는지 등)은 [PLAN.md](PLAN.md)에 자세히 기록돼 있다.
**새 PC에서 처음 설치한다면 [SETUP.md](SETUP.md)부터 볼 것** — 이 프로젝트는 개발 머신 경로가 일부 하드코딩돼 있어 clone만으로는 바로 안 돌아간다.

## 요구 사항

- NVIDIA GPU (VRAM 10GB 이상 권장 — 2B 모델 2개를 순차 로드)
- Python 3.12, [uv](https://github.com/astral-sh/uv)
- ffmpeg (`config.py`의 `FFMPEG_EXE`/`FFPROBE_EXE` 경로를 실제 설치 위치에 맞게 수정)
- (동작 질의용 클립 인덱싱을 쓸 경우) `torchcodec` + FFmpeg 공유 라이브러리를 OS가 찾을 수 있어야 함.
  Windows에서는 `config.py`의 `_DLL_SEARCH_DIRS`에 vcpkg FFmpeg `bin` 폴더와 CUDA Toolkit `bin` 폴더 경로가 하드코딩돼 있다 — 다른 머신에서는 이 경로를 맞게 바꿔야 한다.

## 설치

```powershell
uv venv --python 3.12
uv pip install torch torchvision --index-url https://download.pytorch.org/whl/cu130
uv pip install "transformers>=4.57" "sentence-transformers>=5.4" qwen-vl-utils accelerate pillow numpy
uv pip install torchcodec   # --with-motion(동작 질의)을 쓸 경우에만 필요
```

최초 실행 시 Qwen3-VL-Embedding-2B / Qwen3-VL-Reranker-2B 가중치가 Hugging Face Hub에서 자동 다운로드된다(각 ~4.5GB).
`ask` 커맨드를 처음 쓰면 Qwen3-VL-4B-Instruct(~8GB)가 추가로 내려받아진다.
이후 실행부터는 로컬 캐시가 감지되면 자동으로 오프라인 모드로 전환돼 네트워크를 타지 않는다(`hf_cache.py`).

## 사용법

### 1. 인덱싱 — `vidsearch index <영상>`

영상을 검색 가능한 형태로 미리 가공해 `data/<영상이름>/`에 저장하는 1회성 작업.

```powershell
.venv\Scripts\python.exe -m vidsearch index "c:\videos\sample.mp4"
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--fps` | 1.0 | 프레임 샘플링 간격(초당) |
| `--width` | 896 | 인덱싱용 프레임 폭(px) |
| `--batch-size` | 4 | 프레임 인코딩 배치 크기 |
| `--force` | off | 이미 인덱스가 있어도 다시 만듦. **기존 프레임/썸네일(및 재생성 대상이면 클립)을 먼저 삭제한다** — 프레임 추출이 출력 폴더를 glob으로 수집하므로, 다른 `--fps`/`--width`로 다시 만들 때 이전 파일이 남아 있으면 새 인덱스에 섞여 들어간다 |
| `--with-motion` | off | **동작/모션 질의**("뛰어가는 사람들" 등)를 위한 클립(짧은 비디오) 임베딩 인덱스도 함께 생성. 이미 프레임 인덱스가 있는 영상에 이 옵션만 추가로 다시 실행하면 프레임은 재사용하고 클립 인덱스만 추가된다 |
| `--clip-window` | 4.0 | 클립 윈도우 길이(초) |
| `--clip-stride` | 2.0 | 클립 슬라이딩 간격(초, 50% 오버랩이 기본) |
| `--clip-width` | 640 | 클립 프레임 폭(px) |
| `--clip-batch-size` | 2 | 클립 인코딩 배치 크기 |
| `--no-describe` | off | 영상 요약 생성을 건너뜀. 기본적으로 인덱싱 마지막에 4B 모델(`ask`와 같은 모델)로 영상 전체를 훑어 한두 문장 요약을 만들어 `manifest.json`의 `description`에 저장하고, 웹 UI 목록의 **마우스 툴팁**으로 보여준다. 약 13초(모델 로드 8초 + 생성 5초)가 추가된다. **4B 모델이 아직 캐시에 없으면 자동으로 건너뛴다** — 인덱싱이 예고 없이 8GB를 받게 하지 않기 위함이다(`vidsearch ask`를 한 번 실행해 받아두면 그 다음부터 생성된다) |

### 2. 검색 — `vidsearch search <영상> <질의>`

```powershell
.venv\Scripts\python.exe -m vidsearch search "c:\videos\sample.mp4" "파란 옷을 입은 아이가 뛰어간다"
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--query-en` | - | 질의의 영어 번역(`--bilingual`과 함께 사용) |
| `--bilingual` | off | 한국어+영어 질의를 각각 인코딩해 프레임별 최고 점수 사용 |
| `--recall` | 150 | 임베딩 회수 단계에서 추릴 상위 후보 수 |
| `--gap` | 2.0 | 구간 병합 시 허용 간격(초) |
| `--rerank-top` | 20 | 리랭킹 대상 상위 구간 수 |
| `--no-rerank` | off | 리랭커 생략(빠르지만 부정확) |
| `--no-motion` | off | 클립 인덱스가 있어도 동작 채널 무시 |
| `--top` | 10 | 출력할 결과 개수 |
| `--json` | off | 표 대신 JSON(`{results, timings, total_seconds}`) 출력 |

출력 예시:

```
          time     score  thumb
  00:03:22.000    0.3750  C:\...\data\sample\thumbs\t_00203.jpg

ffplay -ss 202.00 "c:\videos\sample.mp4"

timing
  index load               0.01s    0.0%
  embedder load            5.47s   31.2%
  query encode             1.96s   11.2%
  embedder release         0.16s    0.9%
  frame scoring            0.00s    0.0%
  clip scoring             0.01s    0.0%
  segment merge            0.00s    0.0%
  reranker load            2.17s   12.4%
  rerank (18 segments)     7.60s   43.3%
  reranker release         0.15s    0.9%
  total                   17.53s
```

- **time**: 영상 내 타임코드
- **score / match**: 리랭커를 쓰면 `score`는 **유사도가 아니라 로짓**이다 — 모델이 "이 문서가 질의에 맞나?"에 대해 내놓은 yes/no 토큰의 로그 확률 차이(`1_LogitScore`). 그래서 값이 음수라고 해서 관련이 없다는 뜻이 아니고, 시그모이드를 씌운 값이 실제 관련도다(`match` 열, 로짓 0 = 50%). 절대값은 질의를 어떻게 쓰느냐에 따라 통째로 움직이므로(같은 프레임이 `"병"`은 +0.19, `"a bottle"`은 +0.13) **한 결과 목록 안에서의 순위와 격차만 의미가 있다.**
  `--no-rerank`면 `score`는 임베딩 코사인 유사도(0~1)이며 리랭커 로짓과는 서로 비교할 수 없는 다른 척도다.
- **thumb**: 해당 시점 썸네일 이미지 경로 — VSCode나 탐색기로 바로 열어 확인 가능
- **timing**: 단계별 소요 시간. 모델 로드/해제를 실제 연산과 분리해 재는데, 쿼리마다 체크포인트를 올렸다 내리는 구조(§VRAM)라 콜드 런에서는 로드가 큰 비중을 차지하기 때문이다. `--no-rerank`나 `--recall` 같은 옵션이 어디에 효과가 있는지 이 표로 판단하면 된다.

### 3. 질의응답 — `vidsearch ask <영상> [--start <t> --end <t>]`

이미 인덱싱된 영상에 대해 Qwen3-VL-4B-Instruct에게 자연어로 아무거나 물어본다.
`search`가 "이 장면이 어디 있나"(검색)를 답한다면, `ask`는 "여기서 무슨 일이 벌어지나"(질의응답)를 답한다.
대상 구간의 인덱싱된 프레임 중 최대 `--max-frames`개를 균등 샘플링해 **한 번에 함께** 모델에 넣으므로, 프레임 사이를 비교하는 질문("최대 몇 명")도 가능하다.

```powershell
# 구간 지정 없이 — 영상 전체에서 고르게 샘플링
.venv\Scripts\python.exe -m vidsearch ask "c:\videos\sample.mp4" --question "이 영상을 한 문장으로 요약해줘."

# 특정 구간만 (기본 질문 = 사람 수 세기)
.venv\Scripts\python.exe -m vidsearch ask "c:\videos\sample.mp4" --start 190 --end 198

# HH:MM:SS 형식도 그대로 사용 가능. 한쪽만 줘도 된다(여기부터 끝까지)
.venv\Scripts\python.exe -m vidsearch ask "c:\videos\sample.mp4" --start 00:03:10 --question "이 사람들이 뭘 하고 있어?"
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--start` | 영상 시작 | 구간 시작 — 초(`190`) 또는 `HH:MM:SS(.ms)` / `MM:SS`. `search` 출력의 타임코드를 그대로 붙여넣어도 된다 |
| `--end` | 영상 끝 | 구간 끝 (같은 형식). `--start`/`--end` 둘 다 생략하면 **영상 전체**가 대상 |
| `--question` | 사람 수 세기 질문 | 모델에게 던질 질문. **아무 질문이나 가능** — 기본값이 사람 수일 뿐 카운팅 전용 기능이 아니다 |
| `--max-frames` | 6 | 구간에서 샘플링할 최대 프레임 수(많을수록 정확하지만 느리고 VRAM을 더 씀) |
| `--max-new-tokens` | 512 | 답변 길이 상한. 여기 걸리면 답변이 문장 중간에서 끊기며, 그 경우 출력 끝에 `[잘림]` 이 붙는다 |
| `--json` | off | 답변 대신 JSON(구간·샘플링 시각·질문·답변·`truncated`·단계별 시간) 출력 |

출력 예시:

```
Sampling 6 frame(s) from 190.00s-198.00s: ['190.0s', '191.0s', '192.0s', '193.0s', '194.0s', '195.0s']

7명

이 프레임들에서 동시에 보이는 사람들의 최대 수는 7명이며, ...

timing
  index load              0.00s    0.0%
  frame sampling          0.00s    0.0%
  explainer load          8.54s   69.5%
  generate (3 frames)     3.61s   29.3%
  explainer release       0.14s    1.2%
  total                  12.29s
```

> **주의 — 이건 객체 탐지가 아니다.** VLM에게 "몇 명이야?"라고 텍스트로 물어보는 방식이라, 사람이 겹치거나 군중이 많아질수록 카운트가 부정확해진다.
> 정확한 인원 계수가 필요하면 별도 객체 탐지 모델(YOLO 등)을 붙이는 편이 신뢰도가 높다.
> 또한 이 커맨드는 세 번째 모델(4B-Instruct, ~8GB)을 쓰므로 **최초 실행 시 별도 다운로드**가 발생한다. 다른 모델과 동시에 올라가지 않도록 순차 로드/해제한다.

### 4. 실제 장면 확인

**A. 썸네일을 직접 열기** — `thumb` 경로 또는 `data/<영상이름>/thumbs/` 폴더 안 썸네일을 직접 열람.
검색 없이 특정 시점을 바로 찾아보고 싶다면, 파일명의 5자리 인덱스(`t_00203.jpg` → 203)로 계산할 수 있다:
`t_sec = (인덱스 - 1) / fps` — 기본값(`--fps 1.0`)이면 `t_00203.jpg` = 202초. `frames/`(임베딩용, 896px)와 `thumbs/`(표시용, 320px)는 같은 인덱스로 정렬돼 있고, `--with-motion`으로 만든 `clips/c_00142.mp4` 같은 클립 파일의 정확한 시작·끝 시각은 `data/<영상이름>/clip_meta.jsonl`에서 확인할 수 있다.

`t_sec = (인덱스 - 1) / fps` — 기본값(`--fps 1.0`)이면 `t_00203.jpg` = 202초. `frames/`(임베딩용, 896px)와 `thumbs/`(표시용, 320px)는 같은 인덱스로 정렬돼 있고, `--with-motion`으로 만든 `clips/c_00142.mp4` 같은 클립 파일의 정확한 시작·끝 시각은 `data/<영상이름>/clip_meta.jsonl`에서 확인할 수 있다.

**B. 영상에서 그 지점 재생** — 출력 맨 아래 `ffplay ...` 명령을 실행. `ffplay`가 PATH에 없으면 전체 경로로 실행:

```powershell
& "C:\dev\vcpkg\installed\x64-windows\tools\ffmpeg\ffplay.exe" -ss 202.00 "c:\videos\sample.mp4"
```

### 5. 웹 UI — `vidsearch web`

콘솔 대신 브라우저에서 `search`와 `ask`를 실행하고, 결과를 **썸네일 이미지로 바로 확인**하는 최소 UI다. 표준 라이브러리(`http.server`)만 쓰므로 추가 설치가 없다.

```powershell
.venv\Scripts\python.exe -m vidsearch web --open
```

| 옵션 | 기본값 | 설명 |
| --- | --- | --- |
| `--host` | `127.0.0.1` | 다른 PC에서 접속하려면 `0.0.0.0` (같은 네트워크에 검색 결과가 그대로 노출되므로 신뢰된 망에서만) |
| `--port` | `8000` | 포트 |
| `--open` | 꺼짐 | 시작 후 기본 브라우저 자동 실행 |
| `--videos` | 현재 작업 디렉터리 | 드롭다운에 올릴 영상 파일을 찾을 폴더. 인덱스가 없는 파일도 목록에 나오고 UI에서 바로 인덱싱할 수 있다 |
| `--model-idle` | 600 | 이 시간(초) 동안 작업이 없으면 올려둔 모델을 해제한다. `0`이면 종료할 때까지 유지 |

상단 `search` / `ask` 탭으로 두 모드를 전환하며, 영상 드롭다운은 두 모드가 공유한다.

* 드롭다운에는 **두 종류**가 함께 나온다: `data/` 아래 인덱스가 있는 영상(먼저)과, `--videos` 폴더(기본값: 실행한 작업 디렉터리)에서 발견된 **아직 인덱싱 안 된 영상 파일**. 후자를 고르면 검색/질문 버튼이 비활성화되고 인덱싱 패널이 자동으로 열리므로, 옵션을 정해 `start indexing`만 누르면 된다. 끝나면 그대로 선택된 채 검색 가능한 상태가 된다.
  스캔 대상 폴더는 헤더에 표시된다. 프로젝트 루트에서 실행하면 그 폴더에 영상이 없을 수 있으니, 영상이 다른 곳에 있으면 `--videos "c:\videos"`처럼 지정하면 된다.
  인덱스가 없는 영상도 `▶ play`로 재생은 된다(원본 파일만 있으면 되므로).
* **목록 툴팁** — 드롭다운 항목에 마우스를 올리면 인덱싱 때 생성된 **영상 요약**과 함께 길이·fps·해상도·모션 인덱스 유무·원본 경로가 뜬다. 닫힌 상태의 드롭다운에 올려도 현재 선택된 영상의 같은 내용이 나온다. 요약은 인덱싱 패널의 `describe` 체크박스(기본 켜짐)로 만들어지며, 이 기능이 생기기 전에 인덱싱한 영상은 "설명 없음"으로 표시되고 다시 인덱싱하면 채워진다.
* **재인덱싱** — `⚙ index`를 누르면 현재 인덱스 설정(fps/width/clip 파라미터)이 채워진 옵션 패널이 열린다. 값을 바꾸고 `start indexing`을 누르면 **기존 인덱스를 지우고**(기본 체크) 새 옵션으로 다시 만든다. 인덱싱 중에는 진행 로그가 실시간으로 쌓인다.
  `with-motion`을 끄고 재생성하면 기존 클립 인덱스는 보존되고 프레임 인덱스만 다시 만들어진다.
* **search 모드** — 결과는 썸네일 그리드로 표시되고, 카드를 클릭하면 원본 프레임(896px)이 크게 열린다. 모션 인덱스(`--with-motion`)가 있는 구간은 `▶ clip` 배지가 붙고 **클립을 그 자리에서 재생**할 수 있다(frame/clip 탭 전환). `top` / `no-rerank` / `no-motion` / 영문 병행 질의(`en`)는 `search` 커맨드의 동일 옵션이다.
* **ask 모드** — 질문과 (선택적) `start`/`end` 타임코드를 넣으면 답변이 위에 나오고, 그 답변의 **근거로 모델에 실제로 들어간 프레임들이 아래 그리드에 그대로** 표시된다. 범위를 비우면 영상 전체가 대상이다. 타임코드는 CLI와 같은 형식(`190`, `00:03:10`, `3:10`)을 받는다. `max-tokens`(기본 512)에 걸려 답변이 끊긴 경우에는 답변 박스 테두리가 노랗게 바뀌고 바로 아래에 잘렸다는 안내가 표시되므로, 값을 올려 다시 물어보면 된다.
* **진행률** — 인덱싱·검색·질문 **세 작업 모두** 백그라운드로 실행되고, 진행 중에는 진행률 막대와 `44% · 인덱싱 중 — encode frames 16/20 · 10s 경과` 형태의 현재 단계/경과 시간이 표시된다. 퍼센트는 그 실행이 실제로 거칠 단계들(모델 로드, 인코딩, 리랭킹, 요약 등)에 실측 기반 가중치를 준 계획에서 계산하며, 오래 걸리는 인코딩·리랭킹 단계는 **처리한 개수까지** 함께 보고한다. 브라우저는 `/api/job`을 폴링하므로 페이지를 새로고침해도 진행 중인 작업에 다시 붙는다. 한 번에 한 작업만 돌며(모델이 VRAM에 하나만 올라감), 실행 중 다른 요청은 409로 거절된다.
* **단계별 시간** — 완료 후 각 단계의 소요 시간이 색 막대와 배지로 표시된다(`embedder load` / `query encode` / `rerank` / `explainer load` / `generate` 등, CLI의 `timing` 표와 동일한 값). 어느 단계가 병목인지 바로 보이므로 옵션을 조절할 때 근거로 쓰면 된다.
* **원본 영상 재생** — 영상 드롭다운 옆 `▶ play`를 누르면 선택한 원본 영상을 브라우저에서 바로 재생한다. 결과 확대 창에도 `▶ source` 탭이 생겨 **그 결과의 타임코드부터** 원본을 이어볼 수 있다(`#t=` 프래그먼트). 인덱스만 남고 원본 파일이 사라진 영상은 버튼이 자동으로 비활성화된다.
  서버는 `GET /video/<id>`로 HTTP Range를 지원해 스트리밍하며(응답 1건당 8MiB 상한), 재생 가능한 경로는 `data/` 아래 인덱스들의 manifest에 기록된 원본 경로로만 한정된다.
* 확대 창 아래에 해당 시점의 `ffplay` 명령이 같이 나오므로, 외부 플레이어로 보고 싶으면 복사해서 실행하면 된다.
* **개념 가이드** — 헤더 오른쪽 `ⓘ guide`를 누르면 `GET /guide`로 [guide.html](vidsearch/guide.html)이 새 탭에서 열린다. VLM을 처음 보는 사람 기준으로 이 프로젝트에서 쓰는 개념 — 비주얼 토큰(패치 16 × 병합 2 = 32×32px), `smart_resize`의 조용한 자동 축소, `temporal_patch_size`가 만드는 시간 해상도 하한, 길이와 해상도가 나눠 쓰는 토큰 예산, 듀얼 타워와 크로스 인코더의 차이, VRAM 산수 — 를 도해와 함께 정리한 문서다. 마지막 두 표는 용어 대조표와 **개념 → 이 저장소의 코드 위치** 매핑이다.
  문서는 파이썬 문자열이 아니라 파일이라 요청마다 다시 읽는다. 내용을 고쳐도 서버를 재시작할 필요가 없다.
* **모델 상주** — CLI는 한 번 쓰고 프로세스가 끝나지만 서버는 계속 살아 있으므로, 올린 모델을 다음 작업까지 **그대로 두고 자리가 필요할 때만 내린다**([models.py](vidsearch/models.py)). 12GB 카드 실측 기준:

  | 모델 | 가중치 | 피크 |
  | --- | --- | --- |
  | Embedding-2B | 4.0G | 4.7G |
  | Reranker-2B | 4.0G | +0.7G(랭킹 중) |
  | 4B-Instruct | 8.3G | 9.6G(8프레임) |

  2B 두 개는 함께 상주하고(합쳐 8.6G), 4B는 카드를 혼자 써야 한다. 그래서 **검색을 반복하면 모델을 다시 안 올리고**(25.1s → 4.3s), **질문을 반복해도 4B가 남아 있다**(첫 질문 8.2s → 이후 로드 0s). 검색↔질문을 오갈 때만 교체가 일어난다.
  풀은 고정 규칙 대신 드라이버에 실제 여유 VRAM을 물어보고(이 GPU는 다른 프로그램도 쓴다) 들어갈 때까지 LRU 순으로 내보내며, 첫 로드 때 실측한 사용량으로 추정치를 보정한다. 서버를 켜둔 채 방치하면 `--model-idle` 초 뒤에 모두 해제한다.
* 동시에 들어온 요청은 락으로 순서대로 처리된다. 개인용 단일 사용자 UI를 전제로 한 구조다.

## 동작 원리 요약

1. **인덱싱**: ffmpeg로 프레임(1fps)을 추출하고 Qwen3-VL-Embedding-2B로 벡터화해 저장 — 검색 때마다 영상을 다시 처리하지 않기 위함.
2. **회수(recall)**: 질의를 벡터화해 저장된 프레임 벡터와 코사인 유사도 비교, 상위 후보 추출. 빠르지만 판단이 거칠다(모달리티 갭).
3. **구간 병합**: 시간상 가까운 후보 프레임들을 하나의 "장면 구간"으로 묶는다.
4. **리랭킹**: 상위 구간의 대표 프레임(또는 그 구간이 클립 채널에서 왔다면 클립 자체)을 Qwen3-VL-Reranker-2B 크로스 인코더에 넣어 정밀 재채점 — "빠르지만 대충인 1차 필터 → 느리지만 정확한 2차 검증" 구조.
5. **(선택) 동작 채널**: `--with-motion`으로 만든 클립 임베딩 인덱스가 있으면, 정지 프레임만으로는 판단하기 어려운 동작 질의("뛰어가는", "넘어지는")도 다중 프레임 클립으로 인식해 회수 단계에 함께 반영한다.
6. **구간 질의(`ask`)**: 위 1~5는 "어디에 있나"를 찾는 **검색**이다. 반면 `ask`는 검색을 거치지 않고 사용자가 지정한 구간의 프레임을 생성형 VLM(4B-Instruct)에 직접 넣어 **자연어 답변을 생성**한다 — Embedding/Reranker는 벡터·점수만 내놓을 뿐 텍스트를 만들지 못하므로 별도 모델이 필요하다.
